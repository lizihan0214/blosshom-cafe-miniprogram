# Blosshom & Cafe 微信小程序开发手册

版本：MVP v1.0  
状态：核心范围已确认，可交接开发  
产品定位：单门店、到店自提、微信支付的轻量咖啡点单小程序

## 1. 项目目标

以 **Blosshom & Cafe** 品牌为核心，开发一款温暖、克制、原木风的微信点单小程序。首版以快速上线和低维护成本为优先，只解决以下核心问题：

1. 顾客查看菜单。
2. 选择咖啡规格并加入购物车。
3. 提交到店自提订单。
4. 使用微信支付。
5. 获得取餐号并查看订单状态。
6. 商家通过云控制台和微信支付商户平台处理日常订单。

首版不建设完整商家后台，不做多门店、外卖配送、会员、积分和营销系统。

## 2. 品牌与视觉规范

### 2.1 商标解读

当前商标由以下元素组成：

- 英文名称：`Blosshom & Cafe`
- 主色：深咖啡棕
- 背景：暖白、奶油白
- 图形：细线花朵标志
- 气质：优雅、自然、安静、轻法式、女性友好

小程序界面将延续商标的留白感和细线条气质，不使用过重阴影、强烈渐变和高饱和色。

### 2.2 建议色板

| 用途 | 色值 | 说明 |
|---|---:|---|
| 品牌主色 | `#5A3826` | 商标文字、主按钮、重点价格 |
| 深咖啡色 | `#34261F` | 标题和主要正文 |
| 奶油背景 | `#F7F3EB` | 页面主背景 |
| 卡片背景 | `#FFFDF8` | 商品卡片、订单卡片 |
| 浅木色 | `#C7A27C` | 辅助按钮、分隔元素 |
| 花叶绿 | `#68705A` | 营业状态、完成状态 |
| 次级文字 | `#8D7D70` | 商品描述和辅助说明 |
| 分割线 | `#E8DED1` | 卡片和输入框边界 |

### 2.3 字体策略

- 品牌名称和一级标题：高对比衬线字体风格。
- 中文正文：系统字体 `PingFang SC`，保证微信端清晰度。
- 商品名称：中等字重。
- 按钮和价格：半粗字重，不使用大面积全大写英文。
- 商标字样优先作为图片使用，不在代码中依赖某个商业字体。

### 2.4 商标素材要求

当前 PNG 可用于设计阶段，但不建议直接作为正式上线素材：

- 图片右下角带有“豆包AI生成”水印。
- 背景不是透明背景。
- 商标文字与花朵图形尚未拆分。
- 横向字标不适合直接作为小程序头像或底部导航图标。

正式开发前建议补充：

1. 透明背景横版 Logo PNG，建议宽度不低于 1200px。
2. 独立花朵图标 PNG 或 SVG。
3. 小程序头像使用的 1:1 图标版本。
4. 深色背景和浅色背景各一套 Logo。
5. 确认所用字体、图形和名称具备商用权利。

开发阶段可以临时从现有图中提取颜色和构图，但不会把右下角水印带入产品。

## 3. MVP 功能范围

### 3.1 页面

#### 首页

- Blosshom & Cafe 商标。
- 当前门店、营业状态和营业时间。
- 原木风品牌主视觉。
- “开始点单”按钮。
- 2～4 款推荐商品。

#### 菜单

- 分类：咖啡、非咖啡、轻食。
- 商品图、名称、简介和起售价。
- 售罄状态。
- 加入购物车。

#### 商品规格弹层

- 温度：冰、热。
- 杯型：标准杯、大杯。
- 糖度：无糖、半糖、标准糖。
- 数量。
- 规格产生的加价。

不同商品可以限制可选规格，例如美式不显示糖度，部分特饮只支持冰饮。

#### 购物车

- 商品及规格明细。
- 修改数量。
- 删除商品。
- 实时计算总额。
- 进入结算。

#### 确认订单

- 固定门店。
- 到店自提。
- 取餐称呼。
- 联系手机号。
- 订单备注。
- 商品总额。
- 微信支付按钮。

首版收集手机号，用于订单异常、超时未取和门店联系。默认提供手动填写并进行格式校验；如后续使用微信手机号快捷验证能力，需同步更新隐私保护指引和接口权限配置。

#### 支付结果

- 明确区分支付成功、支付处理中、支付失败和用户取消。
- 支付成功后显示取餐号。
- 提供查看订单按钮。

#### 我的订单

- 当前订单。
- 历史订单。
- 取餐号、商品、金额、时间和状态。
- 支付异常时提供“重新查询”入口。

### 3.2 暂不开发

- 外卖配送和地址管理。
- 多门店切换。
- 会员、积分和储值。
- 优惠券和促销引擎。
- 库存扣减系统。
- 用户评价。
- 自动退款页面。
- 打印机和叫号屏。
- 独立商家管理后台。
- 订阅消息。

## 4. 技术方案

### 4.1 前端

- 框架：uni-app + Vue 2。
- 发布目标：微信小程序。
- 开发工具：HBuilderX、微信开发者工具。
- 基础代码参考：[a313901703/wp-coffee](https://github.com/a313901703/wp-coffee)。
- 许可证：MIT。

基础仓库只复用页面组织、购物车和订单流程思路；UI、品牌素材、支付逻辑、数据模型和安全逻辑均按本项目重新实现。

### 4.2 低成本云端

菜单改为云端动态读取。商家可以在开发完成后，通过 CloudBase 控制台新增、修改、排序、上下架商品及上传图片，无需重新发布小程序。

```text
微信小程序
├── 动态读取菜单
├── 本地缓存最近一次有效菜单
└── 本地购物车

CloudBase
├── categories 分类集合
├── products 商品集合
├── orders 订单集合
├── store_config 门店配置集合
├── Cloud Storage 商品图片
├── getMenu 获取菜单
├── createPayment 创建支付
├── paymentNotify 支付回调
├── queryOrder 支付查单
└── getMyOrders 用户订单

微信支付
└── API v3 小程序支付
```

客户端只读取已启用的分类、商品和门店展示信息，不允许直接写入业务集合。所有订单创建和状态更新必须通过云函数完成；菜单写入由商家在 CloudBase 控制台操作。商品更新后，用户下次进入菜单页或下拉刷新即可获得最新内容；断网时只展示最近一次缓存，并禁止创建支付订单。

### 4.3 配置管理

前端可见配置：

- 小程序 AppID。
- CloudBase 环境 ID。

仅云端保存：

- 微信支付商户号。
- API v3 密钥。
- 商户证书序列号。
- 商户私钥。
- 支付通知地址。

商户私钥、API v3 密钥不得写入小程序代码、Git 仓库或日志。

## 5. 菜单数据规范

首版建立 `categories`、`products` 和 `store_config` 集合。商品名称、价格、规格、图片、排序和上下架状态均从云端读取，因此开发完成后可以动态上传和更新菜单，不需要重新发布小程序。

首版不额外开发商家管理后台，采用成本最低的 CloudBase 控制台维护方式，并提供 JSON/CSV 导入模板和操作说明。若日常维护人员不适合操作云控制台，可在后续增加一个受权限保护的简易商家网页。

```json
{
  "id": "latte-classic",
  "name": "经典拿铁",
  "category": "coffee",
  "description": "醇厚浓缩与鲜牛奶",
  "basePrice": 2200,
  "image": "cloud://environment/products/latte.webp",
  "enabled": true,
  "sort": 10,
  "updatedAt": "serverDate",
  "options": {
    "temperature": ["iced", "hot"],
    "size": ["regular", "large"],
    "sugar": ["none", "half", "regular"]
  }
}
```

金额全部使用“分”为单位的整数，不使用浮点数。创建支付时，云函数必须重新查询 `products` 集合，根据实时价格和有效规格计算金额；订单中保存成交时的商品快照，避免后续修改菜单影响历史订单。

## 6. 订单数据规范

MVP 使用 `categories`、`products`、`store_config` 和 `orders` 四个业务集合，其中 `orders` 保存真实交易记录。

```js
{
  _id: String,
  orderNo: String,
  outTradeNo: String,
  openid: String,
  pickupName: String,
  mobile: String,
  pickupCode: String,
  items: [{
    productId: String,
    productName: String,
    options: Object,
    quantity: Number,
    unitPrice: Number,
    subtotal: Number
  }],
  amount: Number,
  remark: String,
  paymentStatus: String,
  fulfillmentStatus: String,
  transactionId: String,
  createdAt: Date,
  paidAt: Date,
  updatedAt: Date
}
```

### 6.1 支付状态

```text
UNPAID → PAYING → PAID
   └────────────→ CLOSED
PAID → REFUNDED
```

### 6.2 制作状态

```text
PENDING → PREPARING → READY → COMPLETED
                    └──────→ CANCELLED
```

只有支付状态确认是 `PAID` 后，订单才进入制作队列并生成有效取餐号。

## 7. 微信支付流程

1. 顾客点击微信支付。
2. 前端只提交商品 ID、规格、数量和取餐信息。
3. `createPayment` 从云端可信菜单重新计算总额。
4. 云函数创建业务订单及唯一 `outTradeNo`。
5. 云函数调用微信支付 API v3 创建预支付订单。
6. 前端获取支付参数后调用 `wx.requestPayment`。
7. 微信支付通知 `paymentNotify`。
8. 云函数验签并解密通知，幂等更新订单。
9. 前端调用 `queryOrder` 确认最终结果。
10. 支付成功后展示取餐号。

安全原则：

- 不以前端支付成功回调作为最终付款依据。
- 同一支付通知重复到达时只处理一次。
- 相同 `outTradeNo` 不重复创建业务订单。
- 回调处理失败时记录必要日志，但不得记录私钥、完整身份证信息或 API v3 密钥。
- 下单按钮需要防重复点击。
- 支付金额必须由云端计算。

## 10. 隐私与合规

首版收集的数据控制在最低限度：

- 微信 OpenID：识别订单所属用户。
- 取餐称呼：线下交付。
- 联系手机号：订单异常、超时未取及必要的门店联系。
- 订单内容和支付状态：履行交易。
- 订单备注：顾客主动填写。

需要准备：

- 小程序隐私保护指引。
- 用户服务协议。
- 订单和退款说明。
- 门店名称、地址、联系方式和营业时间。
- 正确的小程序服务类目。
- 按平台要求接入交易订单管理能力。

### 13.1 小程序认证操作

微信支付要求小程序完成认证；未认证的小程序不能申请小程序支付权限。建议在 UI 开发期间同步办理，不必等待代码全部完成。

#### AppID 是什么

AppID 是微信为每个小程序分配的唯一应用编号，通常以 `wx` 开头。它用于微信开发者工具识别项目、关联 CloudBase 环境，以及让微信支付确认“哪个小程序正在发起交易”。AppID 不是商户号，也不是密钥。

正在认证并不妨碍查看 AppID。登录[微信公众平台](https://mp.weixin.qq.com/)后，通常可在以下路径找到：

```text
开发与服务 → 开发管理 → 开发设置 → AppID（小程序ID）
```

AppID 可以提供给开发人员；`AppSecret`、API v3 密钥和商户私钥不能通过聊天或普通文档发送。微信支付官方的 AppID 查询路径和绑定说明见：[管理商户号绑定的 AppID](https://pay.wechatpay.cn/doc/v3/merchant/4013287504)。

一般操作流程如下，具体入口名称以微信公众平台当时显示为准：

1. 使用未注册过公众平台的邮箱，在[微信公众平台](https://mp.weixin.qq.com/)注册“小程序”账号。
2. 选择与营业执照一致的主体类型，建议使用实际收款的个体工商户或企业主体。
3. 填写主体、管理员和门店经营信息，完成管理员身份核验。
4. 登录公众平台，在账号设置或微信认证入口发起认证。
5. 按页面要求上传营业执照、经营者或法定代表人资料及其他证明，并完成平台指定的主体校验。
6. 支付页面当时显示的认证费用并提交审核；费用和审核时效以提交页面为准。
7. 注册后即可在“开发管理/开发设置”中查看小程序 AppID；认证通过后再申请支付权限。
8. 在微信支付商户平台申请或使用现有商户号，开通小程序支付权限。
9. 发起 AppID 与商户号绑定，并回到微信公众平台确认授权。
10. 配置 API v3 密钥、商户证书和安全联系人，再进入真实支付联调。

微信支付官方当前明确要求小程序完成认证，并要求商户号与 AppID 绑定；支持申请小程序支付的主体包括个体工商户、企业及其他受支持组织。参考：[微信支付小程序支付接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4015459512)。

注意：主体、管理员、商户号和证书属于商家敏感资料。开发时只需要把必要参数配置到商家自己的云环境，不应通过聊天、普通文档或 Git 仓库传递私钥和 API v3 密钥。

### 13.2 资料何时提供

不需要所有资料都在开发第一天提供。项目会使用占位数据和开发环境先完成界面与普通业务流程，之后再替换正式资料。

| 资料 | 是否可开发后提供 | 最晚时间 |
|---|---|---|
| 小程序 AppID | 可以先使用测试号或开发占位配置；认证中通常也可查询 | 真机联调和上传体验版前，建议现在提供 |
| 小程序认证 | 当前正在办理，可与 UI 开发并行 | 申请小程序支付权限前 |
| 商户号、AppID 绑定 | 可以后提供 | 真实支付联调前 |
| API v3 密钥、商户证书和私钥 | 可以后提供 | 真实支付联调前，仅配置到云端 |
| CloudBase 环境 ID | 可以先用开发环境 | 部署云函数和数据库前 |
| 正式菜单、价格和规格 | 可以后上传 | 体验版验收前 |
| 商品照片 | 可以后上传 | 体验版验收前 |
| 门店地址、电话和营业时间 | 可以使用占位内容 | 提交审核前 |
| 正式 Logo | 可以使用临时设计稿 | 提交审核前必须替换 |
| 隐私指引、退款规则 | 可在开发中准备 | 提交审核前 |

为了让菜单在开发后动态上传，开发阶段会先确定字段结构并创建空的云端集合，同时准备少量演示商品。开发完成后，商家可以继续上传正式商品和图片；菜单内容变化不需要重新发布小程序。只有页面功能、数据字段或交互逻辑发生变化时，才需要发布新版本。

### 13.3 剩余资料操作指引

#### 现在建议提供：小程序 AppID

1. 登录微信公众平台。
2. 进入“开发与服务 → 开发管理 → 开发设置”。
3. 复制 `AppID（小程序ID）`。
4. 只提供 AppID，不提供 AppSecret。

如果暂时找不到 AppID，仍可先开发 UI、菜单组件、购物车和订单页面；只是微信开发者工具真机联调、CloudBase 正式环境关联和支付联调需要稍后补做。

#### 部署云端前：创建 CloudBase 环境

1. 使用该小程序管理员或开发者账号登录微信开发者工具。
2. 打开项目后进入“云开发”。
3. 创建一个开发环境，取得环境 ID。
4. 开发阶段只在该环境创建 `categories`、`products`、`store_config` 和 `orders`。
5. 正式上线前再决定是否另建生产环境。

CloudBase 环境可以在开发云函数前再创建，不阻塞前端界面开发。

#### 真实支付联调前：商户号和支付参数

1. 等小程序认证通过。
2. 在微信支付商户平台申请或确认商户号，并开通小程序支付权限。
3. 发起商户号与小程序 AppID 的绑定，在微信公众平台确认。
4. 在商户平台配置 API v3 密钥并准备商户证书。
5. 将参数直接配置到商家自己的 CloudBase 云函数环境变量或密钥管理中。

商户号可以告知开发人员用于配置；API v3 密钥和商户私钥应由商家管理员直接录入云端，避免经过聊天和 Git 仓库。

#### 体验版验收前：菜单与图片

1. 按提供的 JSON/CSV 模板填写分类、商品名、价格、规格、排序和上下架状态。
2. 在 CloudBase 云存储上传商品图片。
3. 将图片文件 ID 填入商品记录。
4. 在小程序中下拉刷新并核对菜单。

这些内容可以在主要开发完成后上传；首版开发会自带演示数据。

#### 提交审核前：门店、Logo 和经营规则

需要补齐正式门店名、地址、电话、营业时间、无水印 Logo、隐私保护指引、退款规则和取消订单规则。它们不影响前期编码，但会影响最终页面、隐私合规和平台审核，因此必须在提交审核前完成。

### 13.4 开发启动所需的最少信息

目前功能范围、品牌名、手机号、动态菜单和单门店自提均已确认，已经可以开始前端及普通业务开发。

当前最希望优先拿到的是 **小程序 AppID**；如果暂时无法提供，也不会阻塞第一阶段。小程序认证、商户号、支付证书、正式菜单、商品图片和门店资料都可以按上面的时间节点后补。真实支付联调之前，必须完成认证、商户号绑定和云端支付参数配置。

## 14. MVP 验收标准

满足以下条件视为首版完成：

1. 微信开发者工具和真机均可正常运行。
2. 品牌、菜单、购物车和结算页面视觉一致。
3. 顾客能够选择规格并生成正确金额。
4. 微信支付能够真实完成支付。
5. 支付回调能够安全更新订单。
6. 支付成功后能够显示唯一取餐号。
7. 顾客能够查看自己的订单。
8. 商家能够在 CloudBase 控制台动态维护菜单并查询订单。
9. 私钥和密钥未出现在前端代码与 Git 仓库中。
10. 提供环境配置、菜单导入、图片上传、菜单修改和发布说明。

### 17.3 第二轮开发目标

6. 实现用户只能查询本人订单的访问控制。

### 17.4 第三轮开发目标

认证通过并由商家完成安全参数配置后：

1. 接入微信支付 API v3 小程序支付。
2. 实现创建预支付订单、支付参数签名、支付回调验签与解密。
3. 实现支付查单、关单、幂等更新和异常恢复。
4. 支付成功后生成取餐号，并将订单进入制作状态。
5. 完成真机小额支付、取消支付、重复回调和弱网测试。

### 17.5 明确禁止事项

- 不把 AppSecret、API v3 密钥、商户私钥或证书内容提交到 Git。
